# 2026-07-26｜開発ツールの役割分担

## 今日の到達点

- VS Code、ターミナル、シェル、ブラウザの役割を区別できた。
- ターミナルへ入力したコマンドが実行される流れを説明できた。
- `Cmd + P`と`Cmd + Shift + F`を目的に応じて使い分けられた。
- Elements、Console、Networkから問題に合う確認場所を選べた。

## 開発ツールの役割

| 道具 | 主な役割 |
|---|---|
| VS Code | ファイルやコードを探し、読み、編集する。 |
| ターミナル | コマンドを入力し、実行結果を表示する。 |
| シェル | 入力されたコマンドを解釈し、実行を依頼する。 |
| Git・pnpm・Node.jsなど | シェルから呼び出され、実際の処理を行う。 |
| ブラウザ | Web画面を表示し、操作結果や通信状況を確認する。 |

開発中は一つの道具だけを見るのではなく、知りたい内容に合う道具へ移動する。

## ターミナルとシェルの違い

ターミナルは文字の入力と結果表示を行う画面で、シェルはその中でコマンドを解釈するプログラムである。Macでは`zsh`が使われることが多く、VS Codeの統合ターミナルでもzshなどのシェルが動く。

```text
あなた
↓
VS Codeのターミナルへ入力
↓
シェルがコマンドを解釈
↓
Gitやpnpmなどを実行
↓
結果をターミナルへ表示
```

普段直接触るのはVS Codeとターミナルだが、ターミナルの裏側ではシェルが入力を解釈している。

## シェルがコマンドを実行する流れ

例えば、次のコマンドを入力する。

```bash
git status
```

```text
ターミナルが文字を受け取る
↓
シェルがGitを実行する命令だと解釈
↓
Gitがリポジトリの状態を確認
↓
結果をターミナルへ表示
```

`pwd`、`ls`、`git status`、`pnpm dev`なども、ターミナルへ入力し、シェルを通して実行する。シェルは人の入力とOSや各プログラムの間に立つ司令役である。

## VS Codeで試した操作

| 操作 | 役割 | 使う場面 |
|---|---|---|
| `Cmd + P` | ファイル名からファイルを開く。 | 開きたいファイル名が分かっている。 |
| `Cmd + Shift + F` | プロジェクト全体から文字列を検索する。 | 表示文言やコード断片しか分からない。 |

Explorerを順番にたどらなくても、`Cmd + P`なら目的のファイルへ直接移動できる。画面上の文言や関数名から実装場所を探す場合は、`Cmd + Shift + F`を使う。

```text
ファイル名が分かる
→ Cmd + P

表示文字列やコード断片が分かる
→ Cmd + Shift + F
```

## Browser Developer Tools

Developer Toolsは、ブラウザ内で起きていることを確認する観測画面である。Macでは`Option + Command + I`で開ける。今日はElements、Console、Networkの3つを確認した。

### Elements

Elementsでは、表示中のHTML構造と適用されているCSSを確認する。

- 見出し、ボタン、入力欄、カードなどの要素
- 適用されているCSS
- 要素のサイズや余白
- 上書きされているスタイル

表示崩れ、余白、対象要素、適用CSSを調べるときに使う。画面上の要素を右クリックして「検証」を選ぶと、その要素をElements上で確認できる。

Elementsで変更したCSSは一時的な確認用で、リロードすると元に戻る。実際の修正はVS Codeで元のファイルへ行う。

### Console

Consoleでは、ブラウザ側JavaScriptのログとエラーを確認する。

- `console.log`の出力
- `TypeError`
- `ReferenceError`
- `Failed to fetch`
- 画面操作に伴うJavaScriptエラー

ボタンが動かない、一部だけ反応しない、変数の中身を確認したい場合に使う。DB接続やサーバー側処理の問題は、通常は開発サーバーのターミナルやVercelのログも確認する。

### Network

Networkでは、ブラウザから発生した通信を確認する。

| 項目 | 確認すること |
|---|---|
| Request URL | どのURLへ送ったか。 |
| HTTP Method | GETやPOSTなど、どの方法で要求したか。 |
| Status Code | 通信結果が成功か失敗か。 |
| Response | サーバーから何が返ったか。 |

```text
GET /api/candidates
Status 200
→ API通信は成功
```

```text
GET /api/candidates
Status 500
→ APIには到達したが、サーバー側処理で失敗した可能性が高い
```

ボタンを押しても新しい通信が出ない場合は、ブラウザ側で止まっているか、通信を必要としない画面内処理の可能性がある。

## Developer Toolsの使い分け

| 問題 | 最初に見る場所 |
|---|---|
| 見た目、HTML、CSS | Elements |
| 画面内JavaScript | Console |
| API通信、データ取得 | Network |

TalentScanで候補者一覧が表示されない場合は、次の順番で切り分けられる。

```text
画面自体が表示されるか
↓
Consoleにエラーがあるか
↓
NetworkにAPI通信があるか
↓
Statusは200か500か
↓
必要ならサーバーログを見る
```

## 道具ごとの観測範囲

| 道具 | 観測できる範囲 |
|---|---|
| VS Code | コード、ファイル、検索結果、編集内容 |
| ターミナル | コマンド結果、Git状態、開発サーバー、サーバーログ |
| Elements | 画面構造とCSS |
| Console | ブラウザ側JavaScript |
| Network | ブラウザから発生した通信 |
| Vercel Logs | 本番環境のBuildとRuntime |

問題の種類によって観測場所を変えると、「画面が動かない」という曖昧な症状を具体的な層へ分解できる。

## 今日実際に確認したこと

- `Cmd + P`でファイル名からファイルを探した。
- `Cmd + Shift + F`でプロジェクト全体の文字列を検索した。
- Browser Developer Toolsを開いた。
- Elementsで画面構造とCSSの確認場所を見た。
- Consoleでブラウザ側のログとエラーの確認場所を見た。
- Networkで通信内容の確認場所を見た。

## 今日説明できるようになったこと

開発中は、問題の種類によって見る道具を変える。コードを探すならVS Code、コマンドやサーバー状態ならターミナル、見た目ならElements、ブラウザ側JavaScriptならConsole、API通信ならNetworkを見る。道具ごとの観測範囲を理解すると、問題箇所を切り分けやすくなる。

ターミナルとシェルは同じものではない。ターミナルは入力と表示のための画面であり、シェルはその中でコマンドを解釈するプログラムである。
