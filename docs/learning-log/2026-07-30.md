## 3つのファイルの役割

| ファイル | 今回整理した役割 |
|---|---|
| `app/candidates/page.tsx` | `/candidates`に対応し、候補者一覧の画面を作る。 |
| `app/api/candidates/route.ts` | `/api/candidates`へのHTTPリクエストを受けるAPIの入口。`GET`や`POST`などの処理を開始する。 |
| `lib/candidates.ts` | 候補者データの取得・検索・加工など、画面やAPIから再利用する共通処理をまとめる。 |

DBがまだない場合、`lib/candidates.ts`からmockデータを取得する構成もあり得る。本日は実装ではなく、各ファイルが受け持つ役割を題材にした。

## URLとファイルパス

URLはブラウザや別システムがアクセスする宛先で、ファイルパスはリポジトリ内の配置場所である。

```text
URL
/api/candidates

対応するファイルパス
app/api/candidates/route.ts
```

URLの先頭へそのままファイル名を足すのではなく、Next.jsの`app`ディレクトリから配置を読む必要がある。

## 理解確認1：`page.tsx`

**質問：** `app/candidates/page.tsx`は、画面、API、共通処理のどれを担当するか。

**本人の初回回答：** `API`

初回は不正解として扱ったが、その後、本人から次の説明があった。

**本人回答：**

`app をapiと誤読したな`

この説明を踏まえると、`page.tsx`の役割を概念として取り違えたというより、`app`を`api`と読み違えた可能性が高い。その後は、次の対応を理解できた。

```text
app/candidates/page.tsx
→ 候補者一覧の画面
```

概念理解の誤りと、文字列の読み違いは分けて評価する。

## 理解確認2：`route.ts`

**質問：** `/api/candidates`へのAPIリクエストを受け取るファイルはどれか。

**本人回答：** `/api/candidates/routes.ts`

APIを受けるファイルを選ぶ方向性は合っていたが、ファイルパスとして次を修正した。

- URLの`/api/candidates`と、リポジトリ内のファイルパスを区別する。
- ファイル名は複数形の`routes.ts`ではなく、単数形の`route.ts`。
- ファイルパスは`app`ディレクトリから書く。

正しいファイルパスは次のとおり。

```text
app/api/candidates/route.ts
```

## 理解確認3：`lib/candidates.ts`

**質問：** 候補者一覧画面と候補者詳細画面の両方で使う「候補者を取得する処理」をまとめる場所はどこか。

**本人回答：** `candidates/lib.ts`

共通処理を`lib`へ置く判断は合っていた。一方、ディレクトリとファイル名の順序を修正した。

```text
lib
→ 共通処理をまとめるディレクトリ

candidates.ts
→ 候補者に関する処理を書くファイル

正しいファイルパス
→ lib/candidates.ts
```

## 本人が説明できた処理の往復

候補者一覧をAPI経由で取得する構成について、本人は各ファイルの役割とデータの戻り道まで説明できた。

**本人回答：**

```text
app/candidates/page.tsx
候補者一覧の画面を作る
        ↓ APIへ候補者データを要求する

app/api/candidates/route.ts
/api/candidatesへのリクエストを受ける
        ↓ 共通処理を呼び出す

lib/candidates.ts
DBまたはmockから候補者データを取得する
        ↓ 結果をroute.tsへ返す

route.ts
JSONとして画面へ返す
        ↓

page.tsx
受け取った候補者を表示する
```

この説明は正しい。処理を一方向ではなく、次の往復として捉えられている。

```text
page.tsx
→ route.ts
→ lib/candidates.ts
→ route.ts
→ page.tsx
```

本日はAPIを経由する構成を題材にした。実装によってはServer Componentの`page.tsx`から`lib/candidates.ts`を直接呼ぶこともあるが、その構成の詳細や使い分けまで理解済みとは記録しない。

## `lib`ディレクトリの広がり

本人から次の質問があった。

**本人回答：**

`これはlibのディレクトリにいろんなtsファイルが入っていくって感じ？`

`lib`には、再利用する処理を機能ごとに分けて置ける。

```text
lib/
├── candidates.ts
├── interviews.ts
├── evaluations.ts
├── bedrock.ts
└── database.ts
```

例えば、`candidates.ts`には候補者の取得・検索・加工、`bedrock.ts`にはBedrock呼び出し、`database.ts`にはDB接続や共通設定を置くイメージである。

ただし、`lib`は何でも入れる場所ではない。

```text
画面を作る
→ app または components

APIリクエストを受ける
→ app/api/.../route.ts

複数の場所から使う共通処理
→ lib
```

ファイルが増えた場合に機能別のサブディレクトリへ分けられることも補足した。本人は説明後に`OK`と回答したが、サブディレクトリへ分割する設計判断まで本人が説明できた記録はない。

## 本日の理解上の変化

学習開始時は、役割そのものだけでなくファイルパスの文字列を正確に読む点に修正が必要だった。

| 初回の読み方 | 修正後 |
|---|---|
| `app`を`api`と読み違えた | `app/candidates/page.tsx`は画面を担当する。 |
| `routes.ts`と複数形で回答し、URLとパスが混在した | `app/api/candidates/route.ts`がAPIの入口。 |
| `candidates/lib.ts`と順序を逆にした | `lib/candidates.ts`に候補者の共通処理を置く。 |

学習後は、`page.tsx`は画面、`route.ts`はAPIの入口、`lib/candidates.ts`は共通処理と区別できた。さらに、取得結果が`lib`から`route.ts`を通って`page.tsx`へ戻ることまで説明できた。
