## 候補者一覧取得の一気通貫フロー

教材サンプル上の処理を、次の順序で統合して確認した。

```text
ブラウザ
↓
page.tsx
↓ fetch("/api/candidates")
GET /api/candidates
↓
route.tsのGET()
↓ getCandidates()を呼ぶ
getCandidates()
↓
DBまたはモック
↓
JavaScriptの候補者データ
↓ Response.json(candidates)
JSON本文を持つHTTP Response
↓
page.tsx
↓ response.json()
JavaScriptの候補者データ
↓ candidates.map(...)
JSX
↓
ブラウザ描画
```

この流れは一つの処理に見えるが、通信・内部関数呼び出し・データ取得・形式変換・画面生成に分かれている。

## 境界ごとの役割

| 境界・処理 | 種類 | 直後に起きること |
|---|---|---|
| ブラウザ → `GET()` | HTTP/API通信 | `fetch()`が`GET /api/candidates`を送り、APIの入口へ到達する。 |
| `GET()` → `getCandidates()` | サーバー内部の関数呼び出し | API処理の中から共通取得処理を呼ぶ。 |
| `getCandidates()` → DBまたはモック | データ取得 | 指定された取得元から候補者データを得る。 |
| `Response.json(candidates)` | Response生成 | JavaScriptの値から、JSON本文を持つHTTP Responseを作る。 |
| `response.json()` | 本文の読み取りと変換 | HTTP ResponseのJSON本文をJavaScriptの値へ変換する。 |
| `candidates.map(...)` | 画面用の変換 | 候補者データをJSXへ変換する。 |

特に、次の2つを同じ通信として扱わない。

```text
ブラウザ → GET()
= HTTP通信

GET() → getCandidates()
= サーバー内部の関数呼び出し
```

## `Response.json()`と`response.json()`の往復

名前は似ているが、処理の方向が異なる。

| 処理 | 入力 | 出力 |
|---|---|---|
| `Response.json(candidates)` | JavaScriptの候補者データ | JSON本文を持つHTTP Response |
| `response.json()` | HTTP ResponseのJSON本文 | JavaScriptの候補者データ |

```text
サーバー側
JavaScriptの値
↓ Response.json(candidates)
HTTP Response
↓ HTTP通信
ブラウザ側
↓ response.json()
JavaScriptの値
```

## 理解確認1：処理順序

**教材サンプル：**

```ts
// page.tsx
const response = await fetch("/api/candidates");
const candidates = await response.json();

// route.ts
export async function GET() {
  const candidates = await getCandidates();
  return Response.json(candidates);
}

// lib/candidates.ts
export async function getCandidates() {
  return db.candidate.findMany();
}
```

**選択肢：**

```text
A：response.json()
B：db.candidate.findMany()
C：fetch("/api/candidates")
D：GET()
E：Response.json(candidates)
```

**本人回答：**

```text
C → D → B → E → A
```

**評価：正解。**

```text
fetchでAPIを呼ぶ
↓
GET()が実行される
↓
DBから候補者データを取得する
↓
HTTP Responseを作る
↓
画面側でResponse本文をJavaScriptの値へ変換する
```

## 理解確認2：`response.json()`の入力・処理・出力

**対象：**

```ts
const candidates = await response.json();
```

**固定条件：**

```text
responseには
Status 200でJSON本文を持つHTTP Responseが入っている
```

**本人回答：**

```text
入力：
responseに入っているHTTPresponse

処理：
response.jsonが帰ってくるのを待機する

出力：
candidates
```

**評価：**

- 入力は正解。
- 出力の方向も合っている。
- 処理では`await`の待機だけでなく、`response.json()`自身が何をするかを加える必要がある。

**正確な整理：**

| 区分 | 内容 |
|---|---|
| 入力 | `response`に入っているHTTP Response |
| 処理 | BodyのJSONを読み、JavaScriptの値へ変換する。`await`でその完了を待つ。 |
| 出力 | 変換された候補者データが`candidates`に入る。 |

「処理」を説明するときは、待つことだけでなく、待っている関数が何をしているかまで述べる。

## 理解確認3：デバッグの切り分け

**固定条件：**

```text
Network：
GET /api/candidates
Status 200

Response：
候補者データは正常

Console：
TypeError: candidates.map is not a function
```

**対象教材コード：**

```ts
const candidates = await response.json();

return (
  <ul>
    {candidates.map((candidate) => (
      <li key={candidate.id}>{candidate.name}</li>
    ))}
  </ul>
);
```

**本人回答：**

```text
問題を観測した場所：
console

最初に詳しく確認する処理：
candidate.map

DBを最初に確認する必要があるか：
ない

理由：
今回のエラーはtypeerrorと出ているため、
DBより先に関数が正しいかを見るべき
```

**評価：**

- 観測場所をConsoleとした判断は正解。
- `map`処理へ絞る方向も正しい。
- DBを最初に確認しない判断も正解。
- DBを除外する根拠は、エラー名だけでなく「どこまで正常だったか」で説明する必要がある。

**正確な整理：**

| 確認項目 | 判断 |
|---|---|
| 問題を観測した場所 | Console |
| 最初に詳しく確認する処理 | `candidates.map(...)`と、直前の`candidates`の実際の値 |
| DBを最初に確認する必要 | ない。 |
| 理由 | NetworkでStatus 200かつResponse正常と確認済みで、エラーがその後の`map`処理で発生しているため。 |

```text
NetworkでStatus 200
↓
API Responseも正常
↓
その後のフロント処理でエラー
↓
Consoleとcandidates.map(...)を確認
```

`TypeError`という名前だけで原因を決めず、正常だった工程を根拠に確認範囲を狭める。

## 今週の本人回答で確認できた理解

- `fetch()`がAPI通信を開始すること。
- `route.ts`がAPIの受け口であること。
- `getCandidates()`が共通取得処理であること。
- モックとDBの違い。
- `findMany()`がDB読み取りであること。
- HTTP ResponseとJSON本文の違い。
- `response.ok`とHTTPエラー処理。
- `throw`で通常処理が中断されること。
- `Response.json()`と`response.json()`の変換方向。
- Networkで500ならサーバー側へ切り分けること。
- Networkで200かつResponse正常ならフロント側処理を疑うこと。
- `fetch → GET → DB取得 → Response生成 → response.json()`という処理順序。

## 今週の概念上の修正点

本人回答の中で、概念として主に次を修正した。

| 修正前の捉え方 | 正確な整理 |
|---|---|
| `fetch()`の出力にDB取得や画面表示まで含める | `fetch()`の直後の出力はHTTP Response。 |
| `getCandidates()`をAPIそのものと捉える | サーバー内部で呼ばれる共通取得処理。 |
| `GET()`から`getCandidates()`もHTTP通信と捉える | サーバー内部の関数呼び出し。 |
| `Response.json()`の出力をJSONそのものと捉える | JSON本文を持つHTTP Responseを作る。 |
| `response.json()`をJavaScriptからJSONへの変換と捉える | JSON本文からJavaScriptの値への変換。 |
| Networkで500ならDB原因と断定する | サーバー側の失敗までは分かるが、原因はログで確認する。 |
| `TypeError`という名前だけで原因箇所を決める | 正常だった工程とエラー発生箇所から切り分ける。 |

## 継続課題：入力・処理・出力

本人から、入力・処理・出力の切り分けを繰り返し練習したいという意向があった。

```text
入力：
その処理が直接受け取るもの

処理：
その行・関数自身が行うこと

出力：
その処理が直後に返すもの
```

後続工程までまとめて書かず、対象の1行または1関数に範囲を限定する。特に次の境界を繰り返す。

```text
URL
↓ fetch()
HTTP Response
↓ response.json()
JavaScriptの値
↓ map / JSX
ブラウザ描画
```

HTTP通信、サーバー内部関数呼び出し、DBアクセス、JSON変換、画面生成も別工程として扱う。
