## 本日確認した全体構造

```text
GET /api/candidates
↓
route.tsのGET()
↓ サーバー内部の関数呼び出し
getCandidates()
↓
モックまたはDB
↓
JavaScript上の候補者データ
↓ Response.json(candidates)
JSON本文を持つHTTP Response
```

今日の重点は、HTTPリクエストを受けるAPIの入口と、入口から呼ばれるサーバー内部の共通処理を混同しないことだった。

## `GET()`と`getCandidates()`の役割分担

| 対象 | 役割 | 担当すること |
|---|---|---|
| `GET()` | HTTP GETリクエストを受けるAPIの入口 | `getCandidates()`を呼び、候補者データを本文に持つHTTP Responseを作る。 |
| `getCandidates()` | 候補者データを取得する共通処理 | モックまたはDBから候補者データを取得し、呼び出し元へ返す。 |

重要な境界は次のとおり。

```text
ブラウザ → GET()
= HTTP/API通信

GET() → getCandidates()
= サーバー内部の関数呼び出し
```

`getCandidates()`自体はAPIではない。`GET()`の内側から通常の関数として呼び出される。

## モックとDBの違い

| 教材サンプル | データの取得元 |
|---|---|
| `return mockCandidates;` | メモリ上またはコード上に用意されたモックデータ |
| `return db.candidate.findMany();` | DB内の`candidate`データ |

`findMany()`はDBから複数レコードを読み取る処理であり、保存処理ではない。

| 処理名 | 代表的な役割 |
|---|---|
| `findMany` | 複数レコードの読み取り |
| `create` | 新規作成 |
| `update` | 更新 |
| `delete` | 削除 |

ただし、コード内に`create`という文字列があるだけでDB保存と断定しない。実際にどのオブジェクトのどの関数を呼び出しているかを確認する。

## 1行の入力・処理・出力

**対象コード：**

```ts
const candidates = await getCandidates();
```

**本人回答：**

```text
入力：getCandidates()を呼び出す
処理：レスポンスを待つ
出力：getCandidatesが返したデータがcandidatesに入る
```

**評価：**

- 入力は概ね正解。
- 「レスポンスを待つ」ではHTTP Responseと混同しやすいため、関数の完了と戻り値を待つ表現へ修正した。
- 出力は正解。
- 対話中の「ナイル」は入力ミスとして扱い、概念上の誤答にはしない。

**正確な整理：**

| 区分 | 内容 |
|---|---|
| 入力 | `getCandidates()`の呼び出し |
| 処理 | `getCandidates()`を実行し、完了して値が返るまで`await`で待つ。 |
| 直後の出力 | 返された候補者データが`candidates`へ入る。 |

ここで待っているのはHTTP通信の`Response`ではなく、サーバー内部関数`getCandidates()`の完了と戻り値である。

**教材サンプル：**

```ts
  return db.candidate.findMany();

```

**本人回答：**

```text
Aの取得元：モックから取得
Bの取得元：DBから取得
B：DBから取得
```

**評価：**

| 確認項目 | 評価 |
|---|---|
| Aの取得元 | 正解 |
| Bの取得元 | 正解 |
| BがDB保存か取得か | 取得と判断できており正解 |

モックとDBの取得元の違い、`findMany()`が読み取り処理であることを区別できた。

## 理解確認：`Response.json(candidates)`

**対象コード：**

```ts
return Response.json(candidates);
```

前提として、`candidates`にはJavaScript上の候補者データが入っている。

**本人回答：**

```text
入力：
JavaScript上の候補者データ

処理：
JavaScript形式の候補者データをJson形式に変換

出力：
HTTPレスポンスをJson型に整形したデータとして返す
```

**評価：**

- 入力は正解。
- 処理は概ね正解。
- 出力では、HTTP Response全体とJSON本文の区別を補足した。

**正確な整理：**

| 区分 | 内容 |
|---|---|
| 入力 | JavaScript上の候補者データ`candidates` |
| 処理 | `candidates`から、JSON形式の本文を持つHTTP Responseを作る。 |
| 直後の出力 | 候補者データをJSON本文に持つ`Response`オブジェクト |

## HTTP Response全体とJSON本文

HTTP ResponseはJSONそのものではなく、通信結果全体である。

```text
HTTP Response
├─ Status
├─ Headers
└─ Body
   └─ 今回はJSON形式の候補者データ
```

**本人の理解：**

```text
HTTP ResponseにはJSON以外にも入っている

レスポンス全体の中で、
本文をJSON形式にしている
```

API側と受け取り側では、JSON変換の方向が異なる。

| 場所 | 処理 | 変換方向 |
|---|---|---|
| API側 | `Response.json(candidates)` | JavaScriptの値 → JSON本文を持つHTTP Response |
| 受け取り側 | `response.json()` | HTTP ResponseのBodyにあるJSON → JavaScriptの値 |

大文字の`Response`はHTTP Responseを作る側で使い、小文字の`response`は`fetch()`で受け取った変数名として使われている。

```text

```

### 処理の修正

全体の流れは理解できている。ただし、`getCandidates()`を「APIで呼び出す」と表現していたため、内部関数呼び出しとして整理した。

```text
getCandidates()をサーバー内部の関数として呼び出す
↓
返された候補者データをcandidatesに入れる
↓
JSON本文を持つHTTP Responseを作る
```

### 出力の整理

本人回答は概ね正解。より正確には次のとおり。

```text

```

## 本日の重要な理解

本日、API通信とサーバー内部処理の境界を明確にした。

```text
ブラウザ → GET()
= HTTP/API通信

GET() → getCandidates()
= サーバー内部の関数呼び出し
```

あわせて、候補者データ、JSON本文、HTTP Responseを次のように整理した。

```text
候補者データ
= JavaScript上の値

Response.json(candidates)
= JSON本文を持つHTTP Responseを作る

HTTP Response
= Status・Headers・Bodyを持つ通信結果全体

response.json()
= BodyのJSONをJavaScriptの値へ変換する
```

## 本人の理解上の継続課題

「入力・処理・出力」の切り分けは前日からの継続課題である。本日は、1行単位では直後の出力を分けられる場面が増えた。

一方で関数全体を対象にすると、次の境界が混ざることがある。

- 関数への入力と、関数内部で呼び出す処理。
- HTTP/API通信と、サーバー内部の関数呼び出し。
- JSON本文と、HTTP Response全体。

今後も次の形式で確認する。

```text
入力：
その処理が直接受け取るもの

処理：
その処理自身が行うこと

出力：
その処理が直後に返すもの
```

特に、対象コードの後続工程まで出力へ含めないことを意識する。
