## デバッグの基本方針

```text
入力は来たか
↓
処理は実行されたか
↓
期待した出力は返ったか
```

また、「観測場所」と「確認するコード・処理」を分ける。

| 分類 | 例 |
|---|---|
| 観測場所 | Console、Network、開発サーバーログ |
| 確認するコード・処理 | `response.json()`、`candidates.map(...)`、`getCandidates()`、`db.candidate.findMany()` |

本人から「場所ってそういうことか」と確認があった。設問上の「場所」はコードの位置ではなく、現象を確認するための観測場所を意味していた。今後は「場所」ではなく「観測場所」と明記する。

## 観測場所の役割

| 確認したいこと | 主な観測場所 |
|---|---|
| ブラウザ上のJavaScript処理 | Console |
| API通信 | Network |
| `route.ts`などサーバー側処理 | 開発サーバーログ |
| データ取得の詳細 | 共通処理・DB・モックのコードと関連ログ |

観測場所で得た事実を使い、次に詳しく読むコードを選ぶ。

## 教材ケース1：Networkで500

**固定条件：**

```text
画面に候補者一覧が表示されていない

Network：
URL：/api/candidates
Method：GET
Status：500
```

**本人回答：**

```text
通信は発生した
次に確認するのは開発サーバーログ

理由：
少なくとも通信が問題ではないため、
次の処理であるDBからのデータ取得を見るべき
```

**評価：**

- 通信が発生したという判断は正解。
- 次に開発サーバーログを見る判断も正解。
- 「通信が問題ではない」は断定が強いため修正した。
- この時点ではDBが原因とはまだ確定できない。

**正確な整理：**

| 確認項目 | 判断 |
|---|---|
| 通信は発生したか | 発生した。Networkに`GET /api/candidates`とStatus 500がある。 |
| 次の観測場所 | 開発サーバーログ |
| 理由 | API処理が正常終了していないため、`route.ts`や`getCandidates()`などのどこで失敗したかを確認する。 |

```text
Networkで500
↓
HTTP通信は発生した
↓
API処理は正常終了していない
↓
サーバーログで失敗箇所を探す
↓
DBが原因かはログを見てから判断する
```

## 教材ケース2：`database connection failed`

**固定条件：**

開発サーバーログに次が表示されている。

```text
database connection failed
```

**教材サンプル：**

```ts
export async function GET() {
  const candidates = await getCandidates();
  return Response.json(candidates);
}

export async function getCandidates() {
  return db.candidate.findMany();
}
```

**本人回答：**

```text
最初に確認する処理：
GET()

理由：
databaseへの接続に失敗している
エラーメッセージが出ているため
```

**評価：**

- DB接続エラーへ注目した理由は合っている。
- `GET()`全体より、実際にDBへ触っている処理へ絞ると確認が速い。

**正確な整理：**

```text
最初に詳しく確認する処理：
getCandidates()内のdb.candidate.findMany()

理由：
database connection failedというログがあり、
教材コード内で実際にDB接続を伴う箇所がここだから
```

この時点で「DBへの保存失敗」とは言えない。

```text
db.candidate.findMany()
→ DBからの読み取り

今回疑うもの
→ DB接続またはDB読み取り時の失敗
```

## 教材ケース3：Status 200だが画面に出ない

**固定条件：**

```text
Network：
GET /api/candidates
Status 200

Response：
候補者データは正常

しかし画面には候補者一覧が表示されない
```

**対象教材コード：**

```ts
const response = await fetch("/api/candidates");

if (!response.ok) {
  throw new Error("候補者の取得に失敗しました");
}

const candidates = await response.json();

return (
  <ul>
    {candidates.map((candidate) => (
      <li key={candidate.id}>{candidate.name}</li>
    ))}
  </ul>
);
```

**本人回答：**

```text
最初に確認する場所：
response.json

APIより後ろで確認する処理：
map((candidate)=

理由：
候補者データは正常である前提から、
その後段での表示のためのマッピングが
失敗している可能性がある
```

**評価：**

- APIより後段を疑う方向性は合っている。
- `response.json()`や`map()`は観測場所ではなく、詳しく確認するコードである。
- 最初の観測場所としてはブラウザConsoleが適切。

**正確な整理：**

| 確認項目 | 判断 |
|---|---|
| 最初の観測場所 | ブラウザConsole |
| APIより後ろで確認するコード | `response.json()`、`candidates.map(...)` |
| 理由 | APIから候補者データが正常に返っているため、その後のJSON変換、JSX生成、`map`処理で失敗している可能性がある。 |

```text
NetworkでStatus 200
＋ Responseの候補者データは正常
↓
APIからの返却までは正常
↓
ブラウザConsoleを見る
↓
response.json()やcandidates.map(...)を確認する
```

## エラーが見えた場所と原因の場所

本日の中心は、「エラーが見えた場所」と「原因が存在する場所」を分けることだった。

```text
Networkで500
→ API処理が正常終了していない
→ 原因の詳細はまだ未確定

サーバーログでDB接続エラー
→ DBアクセス付近を詳しく確認

Networkで200かつResponse正常
→ APIより後段のブラウザ処理を疑う
→ Consoleを見る
```

観測結果は原因を絞る材料であり、一つの情報だけで原因を断定しない。

| 出力 | 期待した候補者データまで到達していない。 |
