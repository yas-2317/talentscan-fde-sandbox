## 候補者一覧取得の全体フロー

教材上の流れとして、次を確認した。

```text
ブラウザ
↓
page.tsx
↓ fetch("/api/candidates")
route.tsのGET()
↓
getCandidates()
↓
モックデータまたはDB
↓
Response.json(candidates)
↓
response.json()
↓
candidates
↓
JSXへ変換
↓
ブラウザが描画
```

| 要素 | 教材上の役割 |
|---|---|
| ブラウザ | ページを開き、生成された画面を描画する。 |
| `page.tsx` | APIへ候補者一覧を要求し、取得結果から画面を生成する。 |
| `route.ts` | HTTPリクエストを受けるAPIの入口。 |
| `getCandidates()` | 候補者データを取得する共通処理。 |
| `mockCandidates` | メモリ上に用意された練習用データ。 |
| `db.candidate.findMany()` | DBから複数の候補者レコードを読み取る処理。 |
| `Response.json(candidates)` | 候補者情報をJSON形式のHTTPレスポンスとして返す。 |
| `response.json()` | 受信したJSON本文を読み、JavaScriptの値へ変換する。 |

## 理解確認と本人回答

### 問1：候補者一覧取得フローの役割

**本人回答：**

```text
1. page.tsxのawait fetchがキックとなって始まる
2. route.ts
3. 共通処理のgetCandidates
4. return Response.json
5. const candidates
```

**評価：** 全体の主要な接続は理解できている。

- `fetch`がAPI通信を開始することを理解している。
- `route.ts`がAPIの受け口であることを理解している。
- `getCandidates()`がデータ取得の共通処理であることを理解している。
- `Response.json()`がJSONレスポンスを返す処理であることを理解している。

「画面を表示するのはどこか」という設問では、次の複数工程が区別されていなかった。

```text
response.json()
→ JSONをJavaScriptの値へ変換する

candidates.map(...)
→ 候補者データをJSXへ変換する

ブラウザ
→ 生成された画面を描画する
```

設問側がデータの受信、JSX生成、ブラウザ描画の境界を明確にしていなかったため、本人回答は誤答として扱わない。

### 問2：`fetch`の入力・処理・出力

**教材サンプル：**

```ts
const response = await fetch("/api/candidates");
```

**本人回答：**

```text
入力：/api/candidates
処理：candidatesから候補者情報を取得する
出力：DBから候補者一覧を取ってきてページ上に表示するためのオブジェクト
```

**評価：** 入力となるAPIパスは正しく特定できた。処理と出力には、その後のサーバー内部処理や画面表示が混在していた。

| 区分 | 正確な整理 |
|---|---|
| 入力 | APIのURL`/api/candidates` |
| 処理 | URLへHTTP GETリクエストを送り、レスポンスが返るまで待つ |
| 出力 | サーバーから返された`Response`オブジェクト |

`fetch`自体がDBから候補者を読み取ったり、画面へ表示したりするわけではない。それらはサーバー内部の処理と、後続のJSON変換・JSX生成が担当する。

### 問3：`route.ts`のGET処理

**教材サンプル：**

```ts
export async function GET() {
  const candidates = await getCandidates();
  return Response.json(candidates);
}
```

**本人回答：**

```text
入力：candidates
処理：candidate情報を取得し、JSON形式で返ってきたものを他のファイルに渡す
出力：JSON形式の候補者情報
```

**評価：** 候補者情報を取得し、JSONとして返す全体目的は理解できている。次の点を修正した。

- `candidates`は入力ではなく、関数内で作られる途中結果。
- `getCandidates()`の結果が最初からJSONとは限らない。
- `Response.json()`が取得結果からJSON形式のHTTPレスポンスを生成する。
- 「他のファイルへ渡す」より、「APIを呼び出した側へHTTPレスポンスとして返す」が正確。

```text
入力
→ GET /api/candidatesへのHTTPリクエスト

処理
→ getCandidates()を呼び出す
→ 候補者情報を取得する
→ JSON形式のHTTPレスポンスへ変換する

出力
→ 候補者情報を含むHTTP Responseオブジェクト
```

### 問4：モックデータとDB取得の違い

**教材サンプル：**

```ts
export async function getCandidates() {
  return mockCandidates;
}
```

```ts
export async function getCandidates() {
  return db.candidate.findMany();
}
```

**本人回答：**

```text
共通点：
APIもとにデータを返す処理であること

1つ目のデータ元：
mockCandidates

2つ目のデータ元：
db.candidate

DBへの保存処理：
ない
```

**評価：** データ元と、DB読み取り・保存の違いを区別できている。

正確には`getCandidates()`はAPIそのものではなく、`route.ts`から呼ばれるデータ取得処理である。共通点は、どちらも呼び出し元へ候補者一覧を返すこと。

```text
1つ目のデータ元
→ メモリ上のmockCandidates

2つ目のデータ元
→ DB内のcandidateデータ

DBへの保存処理
→ なし
```

`findMany()`は複数レコードの読み取りであり、`create`や`update`のような書き込み処理ではない。

## 1つのコードに含まれる役割

本人の自己認識は次のとおり。

```text
構造はなんとなく分かったが、
実際のコードになったときに読み解き切れない
```

現時点の課題は、全体構造を知らないことよりも、短いコードに含まれる複数の役割を分離して読むことにある。

```ts
export async function GET() {
  const candidates = await getCandidates();
  return Response.json(candidates);
}
```

| コード | 役割 |
|---|---|
| `export` | 別ファイルから利用可能にする。 |
| `async` | 非同期処理を含められる関数にする。 |
| `GET` | HTTP GETリクエストを受ける入口。 |
| `getCandidates()` | 別のデータ取得処理を呼び出す。 |
| `await` | 結果が返るまで待つ。 |
| `candidates` | 途中結果を入れる変数。 |
| `Response.json()` | JSON形式のHTTPレスポンスを生成する。 |
| `return` | 処理結果を呼び出し元へ返す。 |

## 本日の理解上の変化

本日の学習後、次を区別して説明できるようになった。

- `page.tsx`がAPIを呼び出す場所。
- `route.ts`がHTTPリクエストを受けるAPIの入口。
- `getCandidates()`がデータ取得の共通処理。
- モックデータとDB取得ではデータ元が異なる。
- `findMany()`はDBの読み取りであり、保存ではない。
- `Response.json()`はサーバー側でJSONレスポンスを作る。
- `response.json()`は受信したJSONをJavaScriptの値へ変換する。
- データ取得、レスポンス生成、JSX変換、ブラウザ描画は別工程。

一方、`fetch`や`GET()`を入力・処理・出力へ分ける際には、後続処理まで一つにまとめる傾向があった。次回は処理の境界を1行ずつ判定する練習を行う。
